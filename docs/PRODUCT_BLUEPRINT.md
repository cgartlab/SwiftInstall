# SwiftInstall 产品蓝图

> 从「批量安装器」升级为「设计驱动的软件发现 + 活书单 + 迁移指导」产品。
> 本文件记录 2026-11 的战略收敛结论，作为后续开发的对齐基准。**变更时同步更新本文件。**

---

## 1. 一句话定位

**「活的书单。」**
一份只收「成熟、免费/开源、且免费版就够用」的软件书单——它会结合**你机器上已装的软件**，告诉你该留什么、该换成什么、怎么安全地换（附最新版本核验的 AI 指导），并一键装好；书单还能分享，别人加载后同样是"针对他机器"的活的清单。

- 市场：中文 Mac 用户先行（架构预留多语言），首发聚焦设计师/创意工作者。
- 形态：Mac 桌面 App（现代前端 + 动效）+ Go 引擎（复用 `sis` 执行层）。
- 核心对象：**书单（Booklist / Preset）**。

## 4. 核心构想：从"静态书单"到"活的书单"

- **静态书单**（awesome-mac / 少数派 / Bundl 集合）：一个固定列表，人人相同，不会变，要自己动手装。
- **活的书单**（我们）：
  1. **环境感知**：读取本机已装（复用 `backend.InstalledSet`），标出"已装/待装/可替换"。
  2. **策展 + 立场**：每一项标注 免费/开源、**免费版是否够用**、它是谁的平替、为什么值得。
  3. **版本核验**：每项带"最近核验日期 + 适用版本 + 来源"，过期自动降级提示。
  4. **可执行**：一键装齐（`sis`），并给"旧工具 → 新工具"的迁移 Playbook。
  5. **可传播**：书单以文件/链接分享，别人加载后依然按他的机器状态呈现"活"的形态。
  6. **设计**：让"浏览一份好书单"本身成为一种愉悦——这是别人抄不走的。

### 4.1 首次启动体检（First-run Audit）—— 冷启动的关键一招

首次启动不做「空列表」，而是：**扫描本机已装软件 → 给客观评价 → 找到对应平替 → 生成「你的现状书单 + 建议书单」。** 用户一打开就得到「针对我」的价值，这是最强的激活点。

**「客观评价」必须可核验，否则是信任 / 法律雷区。** 评定必须基于可观察、可核验的维度，而不是「AI 觉得好用」：

| 维度 | 判定依据 |
|------|----------|
| 授权与成本 | 免费 / 开源 / freemium（抓官方定价页） |
| 免费版是否够用 | 免费版功能清单 vs 需求（明示日期与版本） |
| 维护活跃度 | 最近更新、issue 响应、star 趋势 |
| 隐私 | 是否开源、有无遥测、是否要求联网/权限 |
| 资源占用 | 包体大小、常驻内存（可测） |
| 数据可导出性 | 是否有开放格式导出（能否换出的前提） |
| 更优平替 | 同类中免费/开源且更优的候选 + 理由 |

**措辞铁律**：只说「基于以上可核验维度」的事实与权衡，绝不说「这软件不好」；给事实+取舍，决定权交用户。避免主观贬损与错误断言。

**技术要点**：
- 枚举已装：`/Applications`、`brew list --cask`、`system_profiler SPApplicationsDataType` 等。
- 映射目录：需名称归一（`Visual Studio Code.app` ↔ `visual-studio-code`）；未收录应用礼貌降级为「暂未收录」。
- 隐私：全程本地扫描，**绝不上传安装清单**（既合规，又是卖点）。

## 5. 核心对象：书单（数据模型）

```yaml
booklist:
  id: mac-for-designers
  title: 设计师的 Mac 起步书单
  audience: 平面 / UI 设计师
  curator: cgartlab
  standard: [free-or-oss, free-tier-sufficient, mature]   # 编辑立场
  updated: 2026-11-05
  items:
    - name: Raycast
      role: 启动器 / 效率
      license: free            # free | oss | freemium
      free_tier_enough: true   # 核心判断：免费版是否够用
      alternative_to: Alfred
      why: 免费版已覆盖启动器/剪贴板/窗口管理，几乎无需付费
      brew: raycast
      version_note: 适用于 2026.11 版，免费功能未缩水
      verified_at: 2026-11-05
      sources: [https://www.raycast.com/pricing]
    - name: Capso
      role: 截图 / 录屏
      license: oss
      free_tier_enough: true
      alternative_to: CleanShot X
      brew: lzhgus/tap/capso
      why: CleanShot X 的开源平替，滚动截图/录屏够用
```

**要点**：`free_tier_enough` + `verified_at` + `sources` 三者，是"免费版够用书单"区别于「随便一份清单」的信任基石。

## 6. 编辑标准与变现张力（关键）

**编辑标准**：只收 ①成熟（有维护、够稳）②免费/开源 ③有付费版则**免费版必须够用**。这是价值观，也是品牌。

**张力（必须正视）**：
- 只推免费/开源 → **没有软件返佣**（Ninite/Setapp 靠推付费软件抽成，此路不通）；
- 你帮用户省下的订阅费，正是你赚不到的市场。

**解法：卖"策展 + 便利 + 持续核验 + 管理"，不卖软件。** 定位如**软件界的《消费者报告》**——用户为"省去自己研究、试错、被免费版坑"付费。这条路成立但更难，需接受。

**衍生风险**：freemium 会"变脸"（今日够用、明日锁功能，enshittification），所以**版本核验管线是生死线**。

## 7. 迁移 Playbook（给指导，不代办）

**Playbook 不是一段文字，而是"带版本校验、带可执行步骤、带来源、可被社区纠错"的结构化迁移手册。**

```yaml
playbook:
  from: { app: Sketch, versions: ["99.x","100.x"] }
  to:   { app: Figma,  versions: ["latest"] }
  last_verified: 2026-11-05
  verified_by: human | community | auto
  staleness: fresh | aging | stale
  confidence: high | medium | low
  data_fidelity: { exports_cleanly: [...], loses: [...] }
  steps: [{ title, detail, source_url }]
  sources: [...]
  known_issues: [{ text, reported_by, date }]
```

- 每条 step 必挂 `source_url`，否则降级为"未验证"。
- `last_verified` + `staleness` 是信任基石：用户一眼看到"几号核过、适用哪个版本"——通用 AI 给不了。

---

## 8. 新鲜度与可信度管线（真护城河）

指南/书单最怕过期与瞎编。护城河 = **持续让内容保持最新、可核验**：

1. **AI 起草**：抓官方帮助 / changelog / 定价页 / 版本说明，生成初版。
2. **人工核对**：确认步骤、`data_fidelity`、`free_tier_enough`，打 `verified_at` 与 `confidence`。
3. **定期复检**：定时抓 `sources` 检测变更 → 自动标 `aging/stale`，提醒复核（尤其定价/免费额度页）。
4. **社区纠错**：用户反馈失效/缩水，进复核队列。
5. **覆盖率扩展**：按"需求量 + 可导出性 + 免费成熟度"排序逐项补齐。

> 这是运营工程 + 内容工程，不是一次性代码——也是抄不走的慢资产。AI 只做起草/复检，不替代核对。

## 9. AI 与人工分工

| 环节 | AI | 人工 / 社区 |
|---|---|---|
| 发现/平替 | 语义理解、候选、理由 | 事实核对 |
| 书单 | 起草条目、抓来源、复检变更 | 判断"免费版够不够用"、标版本 |
| Playbook | 起草步骤、复检 | 核对准确性、标日期 |
| **绝不** | 搬运/改写用户数据 | — |

## 10. 商业模式（免费什么，收什么钱）

| 层 | 免费 | 付费 |
|---|---|---|
| 浏览书单 / 发现 / 平替 | ✅ | — |
| 一键装（sis） | ✅ 基础 | — |
| 迁移 Playbook（基础） | ✅ 大部分 | 长尾/新版本优先覆盖（Pro） |
| 环境管理 / 软件栈健康 / 更新提醒 | 基础 | **Pro 订阅 $8–15/月**（Raycast/Setapp 锚） |
| 我的书单云同步 + 变更通知 | — | Pro |
| 团队软件审计 / 标准书单（B2B） | — | 按项目/按人 |

- **收入 = Pro 订阅（管理 + 云同步 + 持续核验）为主；B2B 团队标准书单为辅。**
- 无软件返佣 → 更不能靠"推荐"收费，只能靠"可信策展与便利"。

## 11. 北极星指标（3–6 个月）

1. **书单采用率**：加载书单后完成"一键装/替换"的比例。
2. **替换成功反馈**：用户回填"换成功了"的数量。
3. **社区贡献**：纠错 / 新增书单 / 分享书单的用户数。
4. **留存与传播**：次周回访、自发分享率。

**PMF 信号**：≥ N 次"按书单成功换并反馈"，且出现**自发**的纠错/分享。

## 12. 三阶段路线图

**阶段 0 · 体验验证（先做）**
- "浏览活书单 → 看到本机状态 → 一键装 → 迁移指导"的**高保真动效交互原型**（可点）。
- 目的：先让人"看到"这件事可以多好看、多省心，收集反馈。

**阶段 1 · 可行性 MVP**
- 1 份真实"活书单"（如设计师 Mac 套装）+ 一键装跑通 + 1 对迁移 Playbook。
- 建立书单/Playbook 数据结构 + 半自动核验管线雏形。

**阶段 2 · 产品化**
- 多书单 + 社区贡献/纠错 + 环境管理（Pro）+ 云同步 + 内容飞轮（"XX 的免费平替书单"系列）。

## 13. 风险

- **红海风险**：Bundl/Packd/Macnite/CaskHub 已免费做"策展+一键装" → 必须靠"活书单×设计×版本核验"取胜。
- **变现张力**：只推免费→无返佣、受众付费意愿低 → 靠《消费者报告》式订阅，需验证。
- **内容过时**：免费版会缩水、应用会更新 → 必须建核验管线，否则信任崩塌。
- **转化风险**：只给指导，用户仍需动手 → 用"一键装新版"降低一半摩擦，并用指标盯"真的换了没"。
- **scope 风险**：从 CLI → 消费 App + 内容 + 社区，是家公司级工程量 → 严厉分阶段。
